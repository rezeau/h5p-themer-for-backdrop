the new root and grants cannot reach other databases. Record protected-file hashes,
repository/ref state, listeners and exact source manifests before starting.

## Exact execution sequence for the later authorized stage

1. **Freeze inputs.** Record the reviewed v0.4.1 allowlist, per-file SHA-256, version,
   working-tree state and manifest checksum. Require a later explicitly authorized
   ZIP build and archive verification, or separately approve a source-tree rehearsal
   labelled as such. Source-tree testing must not be called archive acceptance.
   Stop if any reviewed source hash changes. No Git commit is required merely to
   rehearse a frozen uncommitted snapshot.
2. **Create only new resources.** Reject existing root/database/user/evidence paths;
   check the port is unused; record the exact new server command line/PID. Read a
   verified archived backup instead of bootstrapping or exporting a protected live
   site. Verify backup checksums before import. Import only into the new database
   using its own user. Start only the new loopback server; do not restart existing
   servers. Validate guards and path/database identity before fixture work.
3. **Establish an actual existing v0.4.0 baseline.** If the available archive predates
   v0.4.0, first deploy the exact published v0.4.0 module into this disposable clone,
   refresh that clone's hooks/caches and verify it fully before calling it the
   baseline. Require metadata 0.4.0, exact v0.4.0 production source hashes, schema
   1003, Core API 1.28 and installed TrueFalse 1.8.24. No v0.4.1 files may be present.
4. **Complete baseline fixtures before freezing preservation evidence.** Preserve
   existing schema-1/2 custom themes/preset pins. Prepare any missing Small/Medium/
   Large saved profiles, a hidden custom Global Default, published/hidden learner
   choices and learner-enabled mode through normal candidate administration. Use
   existing installed libraries for two distinct TrueFalse activities and unsupported
   Multiple Choice; do not install or qualify new library versions. Provide single,
   two-player, unsupported and mixed pages through candidate-only fixture code that
   never writes Density classes or calls its own resize.
5. **Prove baseline playback and warm caches.** On v0.4.0 verify colors, picker,
   saved Density, answers/scoring/Check/feedback/Retry, and unsupported isolation.
   Confirm no learner Density toolbar. Warm HTML and JS/CSS aggregates with gate
   TRUE, then leave the gate absent/FALSE for initial upgrade. Record both gate
   states and relevant cache refreshes so an upgrade from a warm site is real.
6. **Capture the preservation/rollback checkpoint.** Back up exact module bytes,
   settings, active/staging config, database and fixture files; record SHA-256 and
   matching database identity. Record theme names/values/densities/pins, Global
   Default including hidden status, learner toggle, visibility policy and schema
   1003. Record H5P node/revision/library records and content JSON/file hashes.
   Exclude caches/logs/sessions from immutable comparisons; list expected transient
   writes explicitly. Capture watchdog maximum/log offsets and dependency hashes.
7. **Deploy coherently inside the stopped/quiesced candidate only.** Validate archive
   inventory/path safety/hashes before extracting into a separate new staging folder.
   Replace the complete candidate module from that verified source, retaining the
   v0.4.0 module backup. Resolve every move/delete path and assert it is under the
   candidate before acting. No symlink to the working repository, mixed-version copy,
   uninstall/reinstall, update-hook replay or configuration migration is allowed.
8. **Refresh only the verified candidate.** In its guarded full bootstrap run native
   `module_implements_reset(); backdrop_flush_all_caches();`. Handle opcode caches
   according to the isolated runtime: record disabled opcache or reset/restart only
   this candidate's own process/SAPI. CLI opcache reset is not proof of web-SAPI
   refresh. Never kill/restart shared Apache by process name. Verify metadata 0.4.1
   and actual delivered learner/controller/CSS bytes against the frozen manifest.
9. **Check preservation before scenario edits.** Require exact saved configuration
   hashes/values, schema 1003, Global Default/visibility/pins/learner toggle and H5P
   content/library hashes to match step 6. Require dependency files unchanged. Any
   unexpected difference stops the rehearsal; do not silently repair it. This is
   the upgrade-preservation result, separate from later intentional fixture edits.
10. **Gate matrix.** On fresh pages test absent/FALSE and a nonboolean value such as
    integer 1: no native Density metadata/controller or toolbar, existing color/theme
    behavior intact. Then exact boolean TRUE: saved profiles apply, learner-enabled
    ready qualified players offer controls. With learner selection disabled, no
    learner controls/storage access; global-only saved Density remains supported.
    Refresh candidate output/JS caches and reload between server-policy changes;
    old open pages are not a remote kill-switch test.
11. **Learner behavior.** Verify all three T buttons, Use theme Density, pressed state,
    hidden polite announcements, accepted aligned/wrapping layout and keyboard focus.
    Explicit Small/Medium/Large overrides must survive custom/Core/built-in/default
    color switches. Reset must follow the currently selected theme. Two distinct
    players keep independent answers/feedback/originals while sharing the preference.
    Unsupported Multiple Choice stays unchanged, including on mixed pages; an
    unsupported-only page retains its existing theme picker without Density controls.
12. **All-null and session scenarios.** After the preservation comparison, record any
    intentional fixture edits separately. Use a candidate-only request-local Core/
    built-in configuration (with a supported non-null built-in reference; Backdrop
    ignores null overrides), or ordinary admin changes recorded for restoration.
    Prove delivered global/selectable profiles are all null and toolbar/reset work.
    Test fresh theme mode, same-tab reload/navigation/BFCache restoration and reset,
    malformed stored values and denied storage. Standard opener-copy semantics apply;
    do not promise every duplicated tab starts empty. Restore scenario settings
    explicitly; do not mistake their intentional changes for upgrade migration.
13. **Regression/health.** Repeat incorrect/correct scoring, Check/Retry, retained
    answers/feedback through Density changes, qualified readiness, replacement/reload,
    unsupported/duplicate/nested/external rejection and asset delivery. Check Firefox
    console, new watchdog errors and PHP/server logs against baseline offsets. Repeat
    100%/200% zoom, narrow layout and keyboard checks on the installed candidate.
    Forced colors/screen reader remain NOT TESTED unless actually performed and
    recorded. Reuse complete source regressions only when their frozen source hash
    is identical; the extracted package still needs its own delivery/integrity checks.
14. **Code rollback rehearsal (not yet proven).** First restore the recorded scenario
    settings and remove this clone's learner Density session key, recording both
    actions. Quiesce only this candidate, restore the complete exact v0.4.0 module
    backup and original gate, refresh hook/output/opcode state as in step 8, and
    reload. Verify metadata/source hashes 0.4.0, schema/config/content unchanged,
    existing colors/picker/saved Density/native playback/unsupported isolation and
    absence of the new toolbar. v0.4.0 ignores the new browser Density key; routine
    DB restore must not be required for a code-only rollback. If it fails, stop and
    document the failure. A full candidate DB/config/files recovery uses only this
    candidate's verified backup and is reported separately, not as code rollback.
15. **Return to the reviewed candidate only if included in approval.** Reapply the
    exact same v0.4.1 input and refresh/verify again. Preserve all rollback evidence;
    do not overwrite it. Record whether the candidate is left at 0.4.0 or 0.4.1.
16. **Close evidence and stop.** Compare protected file/source/ref snapshots and all
    dependency hashes, record final candidate identity/process/health, package
    manifest/checksums and PASS/FAIL/NOT TESTED for every gate. Preserve all failures
    and remediation chronology. Report for review; do not commit/tag/push/publish.
